# Verification log

<p class="lead">Every page of a manual is checked against a real device before it is published, and the check is recorded here.</p>

## How a page is verified

- **Facts in prose** (defaults, addresses, names of screens and buttons, what happens after an action) are read back from the device: its web interface, its HTTP API, its console.
- **API examples** are captured by `tools/api_capture.py` from the device, never typed. The firmware version and date of the capture are in `_meta.json` next to the examples and shown on the reference pages.
- **Screenshots** come from the web interface preview (the same UI code the device serves, with mock data) so no bench addresses or passwords appear. When a screenshot shows a state the preview cannot reproduce, it is taken from the device and said so in the caption.
- The record of every check is the table below: the firmware version, the date, how the page was checked and what came of it. The pages themselves carry no marker (Ali, 2026-10-10: no pills on the pages).

## Bench facts a verifier needs

### The original WiCAN on the bench

- The bench WiCAN OBD (device id `4831b7854135`, hardware v3) sits on the bench CAN bus next to the ECU simulator, which answers standard OBD requests (`0100` with every PID supported, `010C` 716 rpm, `010D` 173 km/h, `0105` 21 degrees).
- Its access point is joined from the Pi's `wtest1` radio: `sudo -n nmcli con add type wifi ifname wtest1 con-name wican-docs-obd ssid WiCAN_4831b7854135 wifi-sec.key-mgmt wpa-psk wifi-sec.psk '@meatpi#' ipv4.method auto connection.autoconnect no`, then `sudo -n nmcli con up wican-docs-obd` (`tools/testbench/pi/dut_ap_join.sh` in the firmware repository does the same but waits for a PRO endpoint). The device is then `192.168.80.1` from the Pi, and `ssh -N -L 8081:192.168.80.1:80 rpi001` brings it to `http://127.0.0.1:8081/` on the PC. Autoconnect is off, so after every device restart run `nmcli con up` again; the restart takes about 25 s.
- The bench access point for its station is the P4 board's `WICAN_TEST_AP` (WPA2): the password lives in the Pi's `wican-bench` profile and reads only with `sudo -n nmcli --show-secrets -g 802-11-wireless-security.psk con show wican-bench` (without sudo it is empty, and an empty password sends the device back to factory settings). The device gets `10.42.1.x` from the Pi's dnsmasq and is reachable from the Pi directly; `avahi-resolve -n wican_4831b7854135.local` gives the address.
- The bench broker is mosquitto on the Pi, port 1883, anonymous clients allowed: `mosquitto_sub -h 127.0.0.1 -t 'wican/4831b7854135/#' -v`. Other bench devices publish there too.
- A configuration change is `GET /load_config`, change it, `POST /store_config` (the device restarts 2 s later), wait, re-join, `GET /check_status`. Keep the original document and post it back at the end; `/load_auto_pid` and `/store_auto_data` for the Automate tab.
- Pictures: `python tools/wican_preview/preview.py --preset fresh|station|automate --port 809x`, then `node tools/capture_device.mjs pages|chapters|station|configured --base http://127.0.0.1:809x`; the same script with `--base http://127.0.0.1:8081` takes them from the device.

- The bench device is a station on the bench access point; from the development PC it is reached through an SSH tunnel to the bench Pi: `ssh -N -L 8081:<device address>:80 rpi001`, then `http://127.0.0.1:8081/`.
- Never join a device's own access point from the development PC: that WiFi is the PC's internet uplink.
- Opening the device's serial console may reset it. Prefer the HTTP API and the WebSocket command line for read-backs.
- A settings change from the bench is: GET the document, change it, PUT it, GET it again to confirm it staged, POST `/api/settings/submit` (the device reboots), confirm on the device. Wait for the restart by watching `boot_count` in `/api/status` go up (about 16 s), not for the first answered request.
- A receiver for HTTP destinations runs on the bench Pi as a transient unit: `systemd-run --user --unit doc-receiver python3 /tmp/doc_receiver.py` (a 20-line `http.server` that appends every POST to a log), stopped with `systemctl --user stop doc-receiver`. Do not `pkill -f` a script name over SSH: the pattern matches the SSH session's own shell and the session dies.
